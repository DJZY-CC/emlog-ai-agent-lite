## 一、产品定位

基于 **ReAct Agent 模式**的 emlog 博客智能运维插件。通过大语言模型（LLM）+ Function Calling 工具调用 + 三层记忆系统，让 AI 真正"读懂博客"并执行内容管理操作。

### 核心架构

```
用户输入
→ PromptBuilder（组装 SystemPrompt = SOUL + BLOG上下文 + 用户记忆 + 工具说明）
→ AgentLoop（ReAct 循环：思考 → 工具调用 → 观察 → 再思考，最多3轮）
→ ToolRunner（工具路由 + 权限校验 + 执行 + 结果格式化）
→ LLM API（OpenAI 兼容协议，Function Calling）
→ 返回最终回复 + 工具调用日志
```

### 技术约束

| 约束 | 要求 |
|------|------|
| PHP 兼容性 | 7.4 及 8.1 均需通过 |
| 数据库 | 不修改 emlog 核心表/字段 |
| 插件规范 | 绿色插件（删除时清理所有数据） |
| 函数命名 | 全部以 `ai_agent_` 为前缀 |
| 输入安全 | 使用 `Input` 类，禁止直接 `$_GET/$_POST` |
| 数据存储 | 使用 `Storage` 类（key-value）+ 自建表 |
| 上架要求 | preview.jpg 75×75px，商店封面 500×300px |

### 3.2 数据库表：`{prefix}ai_agent_chat`

> ⚠️ 此表由插件自动创建（启用时），删除插件时自动清理。**不修改 emlog 核心表**。

```sql
CREATE TABLE `{prefix}ai_agent_chat` (
    `id`         INT(11) UNSIGNED NOT NULL AUTO_INCREMENT,
    `session_id` VARCHAR(64)  NOT NULL DEFAULT '',
    `uid`        INT(11) UNSIGNED NOT NULL DEFAULT 0,
    `role`       VARCHAR(20)  NOT NULL DEFAULT 'user',
    `message`    TEXT         NOT NULL,
    `response`   TEXT         NOT NULL,
    `tool_calls` TEXT,
    `created_at` DATETIME     NOT NULL,
    PRIMARY KEY (`id`),
    KEY `idx_session` (`session_id`),
    KEY `idx_uid` (`uid`),
    KEY `idx_created` (`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## 五、已知问题

### 5.1 部分服务器安装后无法启用/禁用插件

| 项目 | 内容 |
|------|------|
| 发现时间 | 2026-07-25 |
| 影响范围 | 部分服务器（如 emlog.djzy.cc） |
| 症状 | 安装后显示启用，关闭后无法重新开启，弹出红圈叉号 |
| 根因 | emlog 后台 CSRF Token 校验失败（`emMsg('Token校验失败')`），非插件代码问题 |
| 可能原因 | PHP session 配置、Nginx 反向代理、PHP-FPM 进程间 session 不同步 |
| 临时方案 | 通过数据库直接修改 `active_plugins` 字段 + 清除缓存 + 重启 PHP-FPM |
| 后续排查 | 需在受影响服务器上检查 session.save_path、PHP-FPM 配置、Nginx session 传递 |

### 5.4 已修复问题归档（v1.0.3）

以下问题在 v1.0.3 中已确认修复，归档备查：

#### ERR-038：callback_init 依赖未加载导致插件无法重新启用

| 项目 | 内容 |
|------|------|
| 发现时间 | 2026-07-25 |
| 影响范围 | 插件禁用后重新启用的场景 |
| 症状 | 插件禁用后尝试重新启用失败，后台报错 |
| 根因 | `ai_agent_callback.php` 中 `callback_init` 函数依赖的外部类/函数在插件重新启用时未正确加载，导致初始化阶段抛出致命错误 |
| 修复方案 | 在 `callback_init` 入口增加依赖检查与防御性加载，确保所需类文件在调用前已就绪 |
| 状态 | ✅ 已修复 |

#### ERR-039：content/cache 目录不可写导致插件启用失败

| 项目 | 内容 |
|------|------|
| 发现时间 | 2026-07-25 |
| 影响范围 | 部分权限配置严格的服务器环境 |
| 症状 | 插件启用时报错，提示目录不可写 |
| 根因 | 插件启用过程中需要写入 `content/cache` 目录，但该目录在某些服务器上权限不足（如 owner 为 www 而进程以 root 运行，或反过来） |
| 修复方案 | 启用前自动检测目录可写性，不可写时给出明确提示并尝试自动创建/修复权限；增加目录不存在时的自动创建逻辑 |
| 状态 | ✅ 已修复 |

#### ERR-040：后台设置保存不生效 — 表单 action 路由错误

| 项目 | 内容 |
|------|------|
| 发现时间 | 2026-07-25 |
| 影响范围 | 后台设置页面保存操作 |
| 症状 | 修改配置后点击保存，页面刷新但配置未实际更新 |
| 根因 | 设置页面表单的 `action` 属性指向了错误的路由地址，导致 POST 请求未到达正确的处理函数，配置写入逻辑未被触发 |
| 修复方案 | 修正表单 `action` 路由为目标处理 URL，确保 POST 数据正确提交到 `ai_agent_setting.php` 的保存逻辑 |
| 状态 | ✅ 已修复 |
